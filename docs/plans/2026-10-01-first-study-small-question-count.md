# 첫 학습 문항 구성과 문항 수가 적을 때의 진행: 조사와 변경 제안

- 작성일: 2026-10-01
- 문서 상태: 제안. server 소유 영역(`practice/`, `analysis/`, 세션 상태, API)과 스펙은 이 문서로 제안만 하고 수정하지 않았다.
- 기준: 스펙 §6.4.4, §6.4.5, §6.4.8, §7.8, 규칙 2·3·8·12. 조사한 코드는 `main` #41까지(#47 등급 변환 정책은 읽기만 함).
- 변하지 않는 것: 문항 수와 대상 배분은 코드, 문항·정답 기준은 LLM 포트, 품질은 Jev. 원문 근거 발화, 사용자 확인 후 생성, 커넥터 스키마 v5 규칙은 그대로다. LangChain이나 웹 검색으로 문항 수를 채우지 않는다.

## 1. 현재 절차와 요청한 절차의 대응

| 요청한 절차 | 현재 구현 | 차이 |
|---|---|---|
| 1. 목표별 후보 수집, 후보마다 목표·기억 항목·근거 발화 연결 | `practice/domain/FirstStudyComposer.candidates`가 §7.8 표대로 후보를 만든다. 근거 발화는 생성 요청 때 대상 항목의 출처 발화로 붙고, 생성기가 그대로 문제의 `evidenceTurns`로 쓴다 | 없음. 출처 발화가 없는 항목은 확인 단계에서 이미 제외된다 |
| 2. 같은 목표·항목 중복 제거, 다른 목표는 별도 후보 | 목표마다 항목당 후보 1개라 같은 목표·항목 중복은 생기지 않는다. 같은 항목을 여러 목표가 겨냥하면(예: 원리 이해와 자기 말로 설명이 둘 다 대표 핵심 사실) 별도 후보가 된다 | 내용 반복 방지는 생성 프롬프트와 Jev 중복 검사에 맡겨져 있었다 → **ai 쪽에서 보완함(§3)** |
| 3. 헷갈린 지점 우선, 다른 목표도 반영, 12개 초과분은 신규, 같은 입력 같은 계획 | 헷갈린 지점 먼저, 그다음 **목표를 고른 순서대로** 채우고 12개에서 자른다. 결정적이다 | 첫 목표의 후보가 많으면 다른 목표가 0문항이 된다 → **제안 4.4** |
| 4. LLM 생성, Jev 검사, 정해진 횟수 재생성, 미통과 문항 비노출 | `QuestionGenerationService`: 단위별 생성 → 검사 → 탈락 대상만 재생성(`max-generations` 3) → 넘으면 출제 보류. 승인된 문항만 API로 나간다 | 없음 |

## 2. 상황별 현재 동작 (확인한 것)

아래는 임시 통합 테스트와 `FirstStudyComposer` 직접 호출로 확인한 결과다(테스트는 커밋하지 않았다).

| 상황 | 현재 사용자에게 보이는 상태 | 문제 |
|---|---|---|
| A. 후보 0개 (예: 경고 핵심 사실이 없는데 "조건과 예외 판단하기"만 선택) | 목표 선택 응답에 이유가 나온다("주의(warning) 핵심 사실이 없어 문제를 만들지 않습니다."). 그런데 곧바로 세션이 `QUESTIONS_READY`가 되고 첫 학습 조회는 `planned=0, questions=[], held=[]` | 문제 생성을 시작해 버린다. 세션이 확인 완료를 지나가서 목표를 다시 고르면 409가 난다 |
| B. 계획 1개·승인 1개 | `QUESTIONS_READY`, `planned=1, questions=[1개], held=[]` | 없음 |
| C. 계획 1개·승인 0개 | `QUESTIONS_READY`, `generating=false, planned=1, questions=[], held=[1개]` | 풀 문항이 없는데 "문제 준비 완료"로 보인다. 다시 만들 방법이 없다(생성은 `CONFIRMED`에서만 되고, 목표 재선택은 409) |
| D. 일부만 승인 | `QUESTIONS_READY`, `questions`에 승인된 것만, `held`에 보류된 자리 | 계획·승인·보류 수를 응답에서 셀 수는 있으나 필드로 구분돼 있지 않다. 완료 조건은 풀이 흐름이 아직 없어 정해지지 않았다 |
| E. 후보 12개 초과 (사실 14, 경고 1, 헷갈린 지점 1 / 기억·조건·오개념 선택) | 계획 12개: 오개념 1 + 기억 11. **조건과 예외 판단하기는 후보 1개인데 0문항**. 남은 항목 4개는 `unplannedItemIds` | 다른 목표가 반영되지 않는다. 0문항이 된 이유도 표시되지 않는다(후보가 있었으므로 `reason`이 null) |
| F. 마지막 문항 오답 후 재확인 | 풀이 흐름(답변 제출, 단계적 피드백)이 아직 구현되지 않았다. #47의 `RatingPolicy`는 힌트 후 재시도(`ASSISTED_RETRY`)를 평가하지 않고, 지연된 재확인(`DELAYED_RECHECK`)을 같은 날 복습으로 평가한다 | 스펙 §6.4.8은 "다른 문제 몇 개 뒤"만 정하고, 끼워 넣을 문항이 없을 때의 규칙이 없다 |

추가로 발견한 것:

- **"생성 중"이 끝나지 않을 수 있다.** 첫 학습 조회의 `generating`은 "계획이 있고 세션이 `CONFIRMED`"로 계산한다. 비동기 생성이 예외로 죽거나 생성 중에 서버가 재시작하면 세션이 `CONFIRMED`에 머물러 계속 생성 중으로 보인다.
- **목표 재선택과 진행 중인 생성이 겹친다.** 생성이 도는 동안 목표를 다시 고르면 계획이 교체되지만 앞선 생성은 계속 돌아, 옛 계획의 자리 번호(`planPosition`)로 문항을 저장한다. 첫 학습 조회는 자리 번호로 문항을 맞추므로 다른 목표의 문항이 새 계획 자리에 보일 수 있다.
- **`LearningGoalIT.choosingGoalsSavesThePlanSetsStrengthAndPublishesTheEvent`가 단독 실행에서 실패한다**(`main`에서도 같음, 3회 중 3회). 테스트에는 생성기가 없어 생성이 즉시 끝나고 세션이 `QUESTIONS_READY`가 되어, 두 번째 목표 선택이 409를 받는다. 전체 실행에서는 타이밍에 따라 통과한다. 위 두 문제와 같은 뿌리다.
- **교정이 없는 헷갈린 지점도 오류 찾기로 계획된다.** 정답의 근거(대화 속 AI 교정)가 없어 생성기가 매번 실패로 돌려주고, 3라운드를 다 쓴 뒤 보류된다.

## 3. ai 쪽에서 고친 것

- **Jev 문제 품질 검사 질문**(`question/application/QuestionQualityQuestions`, ai 소유 초안이던 것). 실제 Jev로 재 보니 정상적인 핵심 사실 문항 5개 중 4개가 탈락했다. 근거성 질문이 "근거 발화에 답이 있는가"로 읽혀 교정이 없는 항목이 낮게 나왔고, 명확성 단계의 가운데가 "쓸 만하지만 다듬을 것"이라 좋은 문항의 확률이 위 두 단계로 갈려 신뢰도가 0에 가깝게 나왔다.
  - 근거성: 정답 기준이 기억 항목이나 교정의 내용과 같은 뜻인지 묻도록 바꿨다. 사용자 발화는 맥락일 뿐이고, 새 상황을 제시해도 정답 기준이 항목 내용이면 통과다.
  - 명확성: 단계마다 서로 다른 결함을 가리키게 했다(무엇을 묻는지 모름 / 정답 기준이 질문의 답이 아님 / 분명하고 채점 가능).
  - 결과(`./gradlew -q questionQualityCheck`, 표본 9개): 기대와 일치 5/9 → 9/9. 통과 표본 근거성 0.36~0.94 → 0.77~0.97, 탈락 표본(없는 사실, 반대 기준) 0.09·0.30 → 0.04·0.04. 기준값(`review.question.*`)은 바꾸지 않았다.
  - 실제 흐름(`liveTest`의 `LiveQuestionGenerationIT`): 3문항 중 승인 1 → 3(하나는 3회차에 승인).
- **생성 프롬프트**(`question-gen-v3`): 같은 기억 항목을 여러 목표가 겨냥할 때 묻는 각도와 형식을 달리하고, 문장만 바꾼 같은 질문을 두 번 내지 않게 했다. 같은 항목의 승인된 문항과의 중복은 기존 Jev 중복 검사가 본다.
- **확인 도구**: `./gradlew -q questionQualityCheck`(문제 품질 검사 질문을 실제 Jev로 측정).

승인 0개가 드물어졌을 뿐 없어지지는 않는다. 아래 제안은 여전히 필요하다.

## 4. server 쪽 변경 제안

### 4.1 후보 0개: 문제 생성을 시작하지 않는다

- `LearningGoalService.choose`에서 계획된 문항이 0개이면 계획을 저장하지 않고 `LearningGoalSet`도 발행하지 않는다. 세션은 `CONFIRMED`에 그대로 둔다.
- 응답은 지금처럼 목표별 이유(`GoalSummary.reason`)를 돌려주되, 선택이 저장되지 않았음을 알 수 있게 한다(예: 422 `no_candidates` 또는 응답에 `saved: false`).
- 다음 행동: 목표를 다시 고른다. 학습 대화를 보강하려면 대화를 이어서 다시 저장한다(확인 완료 뒤에는 세션 내용을 고칠 수 없으므로 새 학습 세션이 된다).

### 4.2 승인 0개: "문제 준비 완료"로 넘기지 않는다

- 생성 결과를 세션 상태와 따로 기록한다. 예: `FirstStudyPlan`에 `generation`(`NOT_STARTED / GENERATING / DONE / FAILED`), 시작·종료 시각, 실행 번호.
- `generateFirstStudy` 끝에서 승인 1개 이상일 때만 `markQuestionsReady`를 부른다. 0개이면 세션은 `CONFIRMED`에 두고 `generation = FAILED`(이유: 전부 보류)로 남긴다.
- 재시도 경로: `POST /api/sessions/{id}/first-study/retry`로 보류된 자리만 다시 생성한다. 횟수 상한을 둔다(예: 세션당 2회). 세션이 `CONFIRMED`에 남아 있으므로 목표를 다시 고르는 것도 가능하다.
- 다음 행동: 다시 만들기, 목표 다시 고르기, 또는 나중에 매일 학습에서 신규 항목으로 만나기.

### 4.3 "생성 중"이 끝나지 않는 경우

- `FirstStudyQuestionTrigger`에서 예외를 잡아 `generation = FAILED`로 기록한다.
- `GENERATING`이 일정 시간(예: 10분)을 넘으면 조회 시 실패로 간주하고 재시도를 열어 준다(서버 재시작 대비).
- 생성이 도는 동안의 목표 재선택은 409("생성 중")로 막거나, 실행 번호를 두어 이전 실행의 결과를 버린다. 문항에 계획 실행 번호를 함께 저장하면 옛 계획의 문항이 새 계획 자리에 보이지 않는다.

### 4.4 12개 초과: 다른 목표도 반영한다

- 헷갈린 지점 문항을 먼저 넣는 것은 그대로 둔다.
- 남은 자리는 목표를 고른 순서로 **한 문항씩 돌아가며** 채운다(같은 목표 안에서는 복습 단위·항목 순서). 입력이 같으면 결과도 같다.
- 위 E의 예라면 오개념 1 + 조건 1 + 기억 10이 된다.
- 후보는 있었지만 상한 때문에 0문항이 된 목표는 이유를 표시한다(`candidates > 0, planned = 0`일 때의 `reason`).
- 교정이 없는 헷갈린 지점은 후보에서 빼고 이유를 표시한다("대화 속 교정이 없어 정답의 근거가 없습니다"). `FirstStudyComposer.Item`에 교정 유무가 필요하다.

### 4.5 일부 승인: 수를 구분해 보여준다

- 첫 학습 조회 응답에 `planned`, `approved`, `held`(개수)를 따로 둔다. 지금의 `questions`·`held` 목록은 유지한다.
- 풀어야 할 문항 수와 완료 조건은 `approved` 기준이다. 보류된 자리는 포함하지 않는다.
- 보류된 자리의 기억 항목은 신규 항목으로 남아 매일 학습에 편성된다(§6.4.4, 지금도 그렇다).

### 4.6 짧은 첫 학습의 재확인 (풀이 흐름 구현 시)

- 확인 문제는 **다른 문항을 N개(초기값 2) 푼 뒤에만** 낸다.
- 오답 뒤에 남은 문항이 N개보다 적으면: 힌트 → 재도전 → 개념 설명까지만 진행하고 그 자리에서 확인 문제를 내지 않는다. 재도전은 `ASSISTED_RETRY`라 평가하지 않는다.
- 기억 상태에는 첫 무도움 시도의 판정만 반영한다. 풀이 경로는 "설명 후 종료(재확인 없음)"로 기록한다.
- 같은 날 재확인: 사용자가 같은 날 다시 들어왔고 마지막 도움 노출로부터 최소 시간(초기값 10분)이 지났으면 `DELAYED_RECHECK`로 낸다. 직전 도움 노출 여부와 경과 시간을 기록한다. 그렇지 않으면 다음 복습 시점은 FSRS가 계산한 대로 둔다.
- 첫 학습 완료 조건: 승인된 모든 문항에 첫 무도움 시도가 기록되면 완료다. 확인 문제와 보류된 자리는 조건이 아니다. 1문항만 풀어도 완료된다.

## 5. 스펙 문구 제안

합의되면 스펙에 반영한다. 스펙을 먼저 고치고 코드를 맞춘다(AGENTS.md).

**§7.8 끝에 추가**

> - 첫 학습은 품질 검사를 통과한 문항 1~12개로 진행한다. 12는 목표별 상한이 아니라 첫 학습 전체의 상한이다.
> - 상한을 넘으면 헷갈린 지점 문항을 먼저 넣고, 남은 자리는 고른 목표 순서로 한 문항씩 돌아가며 채운다. 같은 입력에는 같은 계획이 나온다.
> - 고른 목표에 맞는 후보가 하나도 없으면 문제 생성을 시작하지 않는다. 이유를 표시하고 목표를 다시 고르게 한다.
> - 후보는 있었지만 승인된 문항이 0개이면 세션을 문제 준비로 넘기지 않는다. 결과(전부 보류 또는 생성 실패)를 표시하고 다시 만들 수 있게 한다.
> - 일부만 승인되면 승인된 문항으로 첫 학습을 진행한다. 보류된 자리는 풀어야 할 문항 수와 완료 조건에 넣지 않으며, 계획 수·승인 수·보류 수를 구분해 보여준다.
> - 승인된 모든 문항에 첫 무도움 시도가 기록되면 첫 학습이 끝난다. 1문항으로도 끝낼 수 있다.

**§6.4.8 첫 항목 뒤에 추가**

> - 사이에 둘 다른 문제가 정해진 수(초기값 2)보다 적으면 첫 학습에서는 확인 문제를 내지 않는다. 설명 직후 같은 문제를 바로 다시 내어 독립적인 정답으로 기록하지 않는다. 같은 날 다시 들어와 최소 시간(초기값 10분)이 지났으면 지연된 무도움 재확인으로 묻고, 그렇지 않으면 이후 복습 시점은 FSRS 계산에 따른다.

## 6. 변경 후 상황별 상태와 다음 행동

| 상황 | 사용자에게 보이는 상태 | 다음 행동 |
|---|---|---|
| 후보 0개 | "고른 목표에 맞는 내용이 없습니다" + 목표별 이유. 세션은 확인 완료 그대로 | 목표 다시 고르기, 또는 대화를 보강해 다시 저장 |
| 계획 1·승인 1 | 문제 준비 완료, 1문항 | 1문항 풀이 → 첫 학습 완료 |
| 계획 1·승인 0 | "문제를 만들지 못했습니다(보류 1)". 생성 중 아님, 준비 완료 아님 | 다시 만들기, 목표 다시 고르기 |
| 일부만 승인 | 문제 준비 완료. "계획 5 · 승인 3 · 보류 2" | 승인된 3문항 풀이 → 완료. 보류 2는 신규 항목으로 매일 학습에 |
| 후보 12개 초과 | 문제 준비 완료, 최대 12문항. 목표별 계획 수와 남은 항목 수 표시 | 12문항 풀이. 남은 항목은 신규 항목으로 매일 학습에 |
| 마지막 문항 오답 | 힌트 → 재도전 → 설명 후 첫 학습 완료. "오늘 한 번 더 확인하면 좋아요" 또는 다음 복습 일정 | 같은 날 다시 들어오면 재확인, 아니면 FSRS가 정한 다음 복습 |

## 7. 확인하지 못한 것

- 제안 4.1~4.6은 구현하지 않았으므로 §6 표는 설계상의 결과다.
- F(재확인)는 풀이 흐름이 없어 현재 동작을 실행으로 확인할 수 없었다. `RatingPolicy`의 시도 종류 처리만 코드로 확인했다.
- 품질 검사 질문은 표본 9개와 live 흐름 1개로만 쟀다. 대화 종류가 늘면 `questionQualityCheck` 표본을 추가해 다시 본다.
