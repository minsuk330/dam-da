# 단계적 피드백: 현재 연결 상태와 연동 제안

- 작성일: 2026-10-01
- 문서 상태: 제안. server 소유 영역(`practice/`의 서비스·규칙·API, `frontend/`)은 이 문서로 제안만 하고 수정하지 않았다.
- 기준: 스펙 §6.2, §6.4.5, §6.4.8, §7 5·6단계. 조사한 코드는 `main` #83까지.
- 역할 분리는 그대로다. LLM은 힌트·설명·변형 문제 생성, Jev는 답변 판정과 허용된 다음 행동 선택, 코드는 풀이 상태·FSRS 등급·복습 일정 계산.

## 2. ai 쪽에서 구현한 것

### 2.1 힌트·개념 설명·선행 개념 생성 (`practice/adapter/out/llm/`)

- `LlmFeedbackContentGenerator`가 포트를 구현한다. 프롬프트는 `FeedbackPrompt`(`feedback-content-v1`).
- 힌트: 정답·정답 기준·모범 답안을 알려 주지 않고 떠올릴 방향만 준다. 교정(`correction`)이 있으면 거기서, 없으면 핵심 사실에서 실마리를 가져오고, 이전 답이 어느 방향으로 어긋났는지 짚는다.
- 설명: 헷갈린 지점이면 당시 믿음(`userBelief`)을 먼저 짚고 교정과 비교한다. 경고 항목은 조건과 예외를 단순화하지 않는다.
- 근거: 모델이 돌려준 근거 발화 중 요청에 있던 index만 남긴다. 요청의 근거 발화는 서버가 기억 항목의 출처에서 만들므로 `meta` 발화가 들어오지 않는다. 설명에 남은 근거가 없으면 대상 항목의 근거 발화를 쓴다.
- 코드로 확인하는 것: 본문이 비었는가, 길이 상한(힌트 300자, 설명 1,200자), 힌트에 모범 답안·정답 기준·교정 문구가 통째로 들어 있는가. 어긋나면 `FeedbackGenerationException`이고 서버가 저장된 기본 힌트·설명을 쓴다.
- 다시 요청하지 않는다. 학습자가 기다리는 자리이고 대체할 내용이 이미 있다.
- `./gradlew test`에서는 빈을 만들지 않고(`@Profile("!test | live")`), 다른 구현이 있으면 물러난다(`@Fallback`).

실제 `gpt-6-luna` 결과(`./gradlew -q feedbackContentCheck`, 표본 4개): 힌트 4개 모두 정답 문구 없이 방향만 제시, 설명 4개 모두 요청에 있던 근거 발화로 연결.

### 2.2 다음 행동 Jev 질문 (`practice/application/NextActionQuestions`)

- 자리표시 문구를 판단 원칙으로 바꿨다. 상세는 `docs/jev.md`의 "다음 행동 선택".
- 실제 Jev 측정(`./gradlew -q nextActionCheck`, 표본 8개): 기대와 일치 3/8 → 8/8. 신뢰도 0.63~0.99로 모두 서버 기준(0.5) 이상.
- #90 반영(첫 학습 도움 후 정답은 규칙이 확인 문제 편성, Jev에 오지 않음): 표본 7개로 바꿔 3회 모두 7/7, 최저 신뢰도 0.56~0.64.
- 고치기 전에는 매일 학습에서 처음 틀린 항목을 신뢰도 0.86으로 "개념 설명"으로 골랐다. 스펙 §6.4.8의 "틀린 항목을 그날 큐 끝에 한 번 더"와 어긋나는 선택이었다.

## 3. server 쪽 연동 제안

### 3.1 피드백을 거치지 않고 다음 문제로 넘어가지 못하게 한다

- 현재: `PracticeService.next`는 현재 제시에 시도가 하나라도 있으면 다음 문제를 낸다. 피드백(`POST .../feedback`)을 불렀는지는 보지 않는다. 화면(#75)은 항상 부르지만, 서버만 보면 오답 뒤에 힌트·설명·확인 문제 편성 없이 넘어갈 수 있다.
- 제안: `next`에서 마지막 제시의 피드백 상태를 확인한다. 피드백 기록이 없거나 마지막 행동이 넘어갈 수 있는 것(`ADVANCE`, `RELEARN_TODAY`, `GENERATE_VARIANT`, `REQUEST_CONFIRMATION`)이 아니면 409를 돌려준다. 힌트를 본 뒤(`GIVE_HINT`) 재도전 없이 넘어가는 것도 여기서 막힌다.
- 대안: `next` 안에서 피드백을 대신 결정한다. 다만 이러면 힌트·설명이 화면에 보이지 않은 채 노출로 기록되므로 권하지 않는다.

### 3.2 남은 문제가 적을 때의 확인 문제

- 현재: 설명 뒤의 확인 문제를 큐 끝에 넣는다(`PracticeSession.enqueueRecheck`). 틀린 문제가 마지막 문제였다면 확인 문제가 곧바로 다음에 나온다. 방금 본 설명을 옮겨 적는 답이 `DELAYED_RECHECK`로 평가된다.
- 제안: `docs/plans/2026-10-01-first-study-small-question-count.md` §4.6과 같다. 사이에 둘 다른 문제가 정해진 수(초기값 2)보다 적으면 그 풀이에서는 확인 문제를 편성하지 않고, 이후 복습 시점은 FSRS 계산에 따른다. 같은 날 다시 들어와 최소 시간이 지났으면 그때 재확인한다.

### 3.3 그 밖에 남아 있는 것

- 판정 서비스 장애로 판정하지 못한 시도(`JudgmentStatus.FAILED`)를 같은 시도로 다시 판정하는 경로가 없다. 그 항목은 등급 없이 남아 나중에 신규 항목으로 다시 나온다.
- `verdict`가 `met`인데 Jev가 질문 오독(`misread`)을 높은 신뢰도로 고른 경우 지금은 등급에 반영된다. `AnswerJudgment`가 오독을 `not_met`일 때만 넘기기 때문이다.
- 문항 자체가 모호하다는 선택(`question_unclear`)은 기록만 되고 보류로 이어지지 않는다.
- 연속 2회 보류로 자동 출제에서 빠진 항목(`autoQuestionsPaused`)을 사용자가 볼 수 있는 조회 경로가 없다.

## 4. 확인하지 못한 것

- 화면을 띄워 오답 → 힌트 → 재도전 → 설명 → 확인 문제를 실제 백엔드와 실제 생성기로 끝까지 눌러 보지 않았다. 이 PC에 Docker가 없어 PostgreSQL을 띄우지 못했다. 생성기와 다음 행동 선택은 live 테스트(`LiveFeedbackIT`)로 각각 확인했다.
- 힌트의 정답 노출 검사는 문구가 통째로 들어간 경우만 잡는다. 표현을 바꿔 정답을 알려 주는 힌트는 프롬프트에 맡겨져 있다.
- 다음 행동 질문은 표본 8개로만 쟀다. 문제 유형과 시도 경과가 다양해지면 표본을 늘려 다시 본다.
