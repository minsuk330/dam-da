# 페르소나와 도메인 스토리

- 작성일: 2026-10-01
- 문서 상태: 확정. 요구사항과 이슈는 이 문서의 단계에서 도출한다.
- 기준 문서: [플랫폼 기획](ai-conversation-learning-review-platform.md). 이 문서와 다르면 기획 문서를 따른다.
- 해커톤 주제: "우리가 바꾸는 캠퍼스의 하루" — AI를 활용해 대학생활을 더 편리하고, 유용하고, 새롭게 만드는 서비스

## 1. 페르소나

### 지원, 경영학과 2학년

| 항목 | 내용 |
|---|---|
| 상황 | 전공 수업(회계원리, 경영통계)과 교양 데이터베이스 수업을 듣는다. 중간·기말고사가 있고 공모전·대외활동을 병행한다. 전공은 특정하지 않는다. |
| AI 사용 | 주 5~10회. 개념을 파고드는 대화("표준편차랑 표준오차 차이가 뭐야?", "그럼 이 경우는?")와 과제 해결 중 개념이 섞이는 대화(과제 풀이, SQL 오류 해결)가 비슷한 비율이다. |
| 문제 | 대화할 때는 이해했다고 느끼지만 시험 때 같은 걸 다시 물어본다. 대화는 목록에 묻히고, 따로 정리할 시간과 의지가 없다. |
| 하루 | 수업 후 공강이나 저녁에 AI와 공부하고 "학습에 넘겨줘"로 저장한다. 통학 지하철과 수업 사이에 휴대폰으로 3~5분 매일 학습을 한다. |
| 동기 | AI로 배운 내용이 휘발되지 않고 오래 남는 것. 습관과 연속 학습 기록. |
| 하지 않는 것 | 노트 정리, 카드 직접 만들기, 매번 "퀴즈 내줘"라고 요청하기. |
| 성공 장면 | 2주 뒤 시험에서 그 개념을 스스로 설명할 수 있다. |

### 요구사항에 미치는 영향

- 매일 학습은 모바일 우선이며 기본 시간 예산은 5분이다. 서술형 문제도 모바일에서 입력할 수 있어야 한다.
- 매일 학습 알림은 통학 시간대에 맞출 수 있어야 한다.
- 문제 해결 대화에서도 학습 내용을 추출해야 한다(AI 영역).
- 데모 데이터는 CS 대화(InnoDB 잠금)와 비CS 대화(경영통계의 표준오차)를 함께 쓴다.
- 시험일 등록과 마감 전 집중 복습은 백로그다.

## 2. 표기

- **행위자**: 지원(학습자), Claude, 플랫폼, Jev, LLM, FSRS 스케줄러, 알림
- **업무 객체**: 학습 대화, 사용자 발화, 학습 세션, 복습 단위, 기억 항목, 문제, 풀이 시도, 복습 기록, 매일 학습 큐
- 각 단계 끝의 `→ 이벤트`는 기획 문서 §8.4의 도메인 이벤트다.

## 3. 스토리 1: 대화 저장 → 확인 → 첫 학습 → 기억 상태 초기화

1. 지원이 교양 DB 수업이 끝난 뒤 공강에 Claude와 InnoDB 잠금에 대해 대화한다. 중간에 "스캔하고 락을 거는 게 아니라?"라고 물었다가 AI에게 교정받는다.
2. 지원이 Claude에게 "이거 학습에 넘겨줘"라고 요청한다.
3. Claude가 사용자 발화 목록과 복습 단위를 `save_learning_session`으로 플랫폼에 보낸다(기획 §7.6).
4. 플랫폼이 스키마를 검증한다.
   - 구조 오류가 있으면 오류를 돌려보내고, Claude가 고쳐서 다시 보낸다.
   - 통과하면 학습 대화를 `model_transcribed`로 저장하고 접수했다고 응답한다. → `ConversationSubmitted`
5. 플랫폼이 학습 세션을 만든다. 복습 단위마다 핵심 사실과 헷갈린 지점을 각각 기억 항목으로 만든다(§6.4.1).
6. Jev가 복습 단위의 복습 가치와 근거 연결을 검수한다. → `ReviewUnitApproved`
7. 알림이 지원에게 "인덱스와 잠금 학습 내용이 도착했어요"를 보낸다.
8. 지원이 앱에서 발화와 복습 단위를 확인한다. 필요 없는 단위는 빼고, 빠진 발화를 추가한다. 수정하면 플랫폼이 다시 검증한다. → `ReviewUnitsConfirmedByUser`
9. 플랫폼이 확인된 발화의 대화 신호로 기억 항목의 초기 평가를 한 번 정하고, FSRS 스케줄러가 초기 상태를 계산한다(§6.4.2). → `InitialMemoryStateSeeded`
   - AI가 교정하거나 부분 정답으로 판정한 발화(`corrected`·`partial`): Again
   - 확인 질문이나 자기 정리를 AI가 맞다고 한 발화(`confirmed`): Good
   - 그 외: 초기 평가 없음
10. 지원이 학습 목표로 "잘못된 이해 바로잡기"(기본 선택)와 "원리 이해하기"를, 기억 강도로 "개념 이해"를 고른다(§7.8, §6.4.7).
    - 앱이 "이 목표면 하루 약 4분"이라고 예상 부담을 보여준다.
    - 목표 유지율 0.85와 매일 학습의 문제 유형 상한(단답·서술)이 정해진다. → `LearningGoalSet`
11. LLM이 학습 목표별 표(§7.8)에 따라 기억 항목마다 문제와 정답 기준을 만들고, Jev가 품질을 검사한다. 떨어진 문제는 다시 만든다. → `QuestionCandidatesGenerated`, `QuestionApproved`
12. 첫 학습이 열린다. 전체 12문제까지이며 헷갈린 지점 항목(초기 평가 Again)부터 나온다. 넘친 항목은 신규 항목으로 남는다. → `FirstReviewStarted`
13. 지원이 도움 없이 답을 내고 자기평가를 고른다. → `AnswerSubmitted`
14. Jev가 판정한다. 객관식은 플랫폼이 직접 채점한다.
15. 플랫폼이 첫 무도움 시도를 등급으로 바꾸고, FSRS 스케줄러가 상태와 다음 복습 시점을 갱신한다(§6.4.5). → `AnswerEvaluated`, `MemoryStateUpdated`, `ReviewScheduled`
16. 틀렸다면 힌트 → 재도전 → 개념 설명 → 확인 문제 순서로 진행한다. → `InterventionSelected`
    - 플랫폼은 이 경로를 기록만 하고 등급은 바꾸지 않는다.
    - 확인 문제는 다른 문제 몇 개 뒤에 나오고, 같은 날 재확인으로 기록된다(§6.4.8).
17. 완료 화면에 확인한 항목, 기억 게이지, 다음 복습 일정이 나온다. → `ReviewCompleted`

## 4. 스토리 2: 매일 학습 → 판정 → 등급 변환 → 다음 복습 시점

1. 7일 뒤 아침 통학 시간, 알림이 "오늘의 학습 · 약 5분"을 보낸다. → `ReviewBecameDue`
2. 플랫폼이 모든 세션(DB 잠금, 경영통계의 표준오차)의 기억 항목에 대해 R을 계산하고 후보를 모은다(§6.4.4).
   - R이 목표 유지율 아래로 떨어진 항목
   - 보류된 항목
   - 오늘 다시 확인해야 하는 항목
3. 플랫폼이 매일 학습 큐를 만든다. → `DailyQueueBuilt`
   - 복습 후보를 우선순위 (1 − R) × 가중치로 정렬하고, 같은 복습 단위 항목은 하루 1개만 넣는다.
   - 복습 분량을 먼저 채우고, 남은 예산 안에서 신규 항목을 최대 3개 넣는다.
   - 5분 예산에 맞춰 자르고 두 세션을 섞는다.
4. 플랫폼이 항목마다 문제를 고른다.
   - 복습 항목은 안정도(S) 사다리에 맞는 유형(§6.4.6), 신규 항목은 학습 목표에 맞는 유형(§7.8)이다.
   - 기존 승인 문제가 없으면 LLM이 변형 문제를 만들고 Jev가 검수한다. → `VariantQuestionGenerated`
5. 지원이 지하철에서 문제를 푼다. 플랫폼이 답변 직전의 예측 R을 기록한다. → `AnswerSubmitted`
6. Jev 판정 → 등급 변환 → FSRS 갱신이 이어진다. → `AnswerEvaluated`, `MemoryStateUpdated`, `ReviewScheduled`
   - 예: 표준오차 문제에서 대화 때와 같은 오개념이 다시 나오면 `not_met + contradiction`, 등급은 Again이고 오개념 재발로 기록된다.
7. 틀린 항목은 짧은 피드백(확인 문제 생략)을 받고, 그날 큐 끝에 한 번 더 나온다(`relearn_today`, §6.4.8).
8. Jev가 `unable_to_judge`를 내면 기억 상태 갱신을 보류한다. 그 문제는 품질 검사로 돌려보내고, 다음 큐에서 변형 문제로 다시 묻는다.
9. 큐를 끝내면 연속 학습 일수가 1 오르고 기억 게이지가 갱신된다(§7.7). → `StreakUpdated`
10. (백그라운드) 복습 기록이 쌓이면 옵티마이저가 개인 매개변수를 학습하고 검증한다. 예측이 개선된 경우에만 적용하고, 항목별 상태를 다시 계산한다(§6.4.9).
