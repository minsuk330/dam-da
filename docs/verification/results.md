### C0 상세: 사용자 발화 누락

누락된 발화:

```text
그러면 full scan전에 하나씩 찾아보면서 lock을 거는게 맞지?
스캔 하고 락을 거는게 아니라?
```

- **누락 구간**: 모델의 도구 인자 생성 단계. ngrok에 남은 Claude 원본 `tools/call` 요청에서도 `userTurns` 19개(index 1~19 연속), `totalUserTurns` 19였고, 서버 저장본과 완전히 같았다. 서버와 전송 구간은 문제가 없다.
- **`totalUserTurns` 무력화**: 모델이 발화 수를 19로 보고하고 번호를 1부터 다시 매겨서, 개수 불일치로는 누락을 감지할 수 없었다.
- **누락 위치**: 실제 대화의 5번째 사용자 발화. 수신본 4번("그러면 보통 인덱스가 없을 경우에는 전부를 잠궈?")과 5번("정리 …") 사이이며, 이후 발화의 index가 하나씩 당겨졌다.
- **유력한 원인 (추정)**: 확인성 질문과 바로 다음 정리 발화(수신본 5번 "각각 하나씩 돌면서 잠금을 하고…")의 의미가 겹쳐, 모델이 중복으로 보고 병합했다. 해당 내용은 assistantSummary §2("읽기 → 잠금 → 판정")에 반영되어 있어 모델이 구간 자체를 놓친 것은 아니다.
- **영향**: 빠진 발화가 사용자가 헷갈린 지점(오개념 신호)이었다. spec §5.1의 차별화 신호가 가장 먼저 손실되는 유형이다.
- **시사점**: 도구 설명으로 "요약·병합 금지"를 지시해도 약 5%(1/20) 누락이 발생했다. spec §7.3 대응 3(앱 확인 단계 사용자 검증)과 §7.5(공유 링크 원문 보강)가 필수다.

#### 실험 A: 같은 대화에서 재저장 요청

- 방법: 같은 Claude 대화에서 "다시 복습에 넣어줘" 전송 (도구 설명 변경 없음)
- 결과: 2차 호출(`2e53a4ce`)도 19/19, 정답 대비 `DIVERGED` 19/20, 같은 5번째 발화 누락
- 1차 호출과 사용자 발화 19개, assistantSummary 1,477자가 바이트 단위로 동일했고, 새 요청 발화("다시 복습에 넣어줘")도 포함되지 않았다.
- 해석: 모델이 대화를 다시 읽지 않고 컨텍스트에 남은 1차 도구 호출 인자를 재사용한 것으로 보인다. **독립 시행이 아니므로 재현성 근거로 쓸 수 없다.**
- 시사점: 같은 대화에서 재저장을 요청해도 누락이 교정되지 않는다. 재현 실험은 저장 요청 메시지를 수정(edit)하거나 응답을 재생성(retry)해 1차 호출이 없는 분기에서 진행한다.

#### 실험 A-2: 이전 호출 재사용 금지 후 재저장 (독립 시행)

- 방법: 저장 요청을 "복습에 넣어 주는데 이전에 생성한 context활용하지 말고 새로 내용 생성해서 넣어줘"로 보냄
- 결과: 3차 호출(`0e8c4e5f`) 19/19. 정답 대비 학습 발화 19개 중 18개 일치, **같은 5번째 발화 다시 누락**. (`missing [5, 20]`, `extra [19]` 중 20·19는 저장 요청 문장이 바뀐 것으로, 누락이 아니다.)
- 독립 시행 근거: assistantSummary가 2,256자로 새로 작성됐고(1·2차는 1,477자 동일), 새 저장 요청 문장이 포함됐다.
- 요약에는 "잠금은 스캔이 끝난 뒤 한꺼번에 거는 것이 아니다"가 있어, 누락된 질문에 대한 답 내용은 반영됐다.
- 해석: **특정 발화가 반복적으로 누락되는 체계적 현상**이다. 무작위 누락이 아니다. 다음 확인 사항은 (1) 모델이 해당 사용자 메시지 자체를 컨텍스트에서 보는지, (2) 도구 설명 강화로 교정되는지다.

#### 진단: 모델이 해당 메시지를 보는가

- "다섯 번째 메시지를 그대로 인용해줘" → "정리 …" 발화를 5번째로 인용. 모델 기준 번호에서 누락 발화가 빠져 있다.
- "'스캔 하고 락을 거는게 아니라'가 들어간 메시지가 있어?" → 처음에는 "없습니다", "다시 확인해봐" 후 "죄송합니다, 있습니다"라며 인용했다.
- 인용문의 첫 줄("…하나씩 찾아보면서 lock을 거는게 맞지?")은 질문에 없던 내용이므로 컨텍스트에서 찾아낸 것이다. 단, 원문 "그러면"을 "그럼"으로 바꿔 인용했다.
- 결론: 메시지는 모델 컨텍스트에 **있다**. 모델이 대화를 나열할 때 이 메시지를 반복적으로 놓치는 **회상 실패**다. 바로 뒤 "정리" 발화와 의미가 겹치는 것이 원인으로 추정된다.
- 추가 발견: 명시적으로 원문 인용을 지시해도 단어 치환("그러면"→"그럼")이 발생한다. 커넥터 수신 발화는 누락과 변형 양쪽 모두 가능하다.

#### 실험 B: 도구 설명 강화 (커밋 `4dd54d0`)

- 변경: "첫 사용자 메시지부터 마지막까지 하나씩 차례로 확인한다. 사용자 메시지 1개는 userTurns 1개다. 앞 질문이나 뒤 정리 발화와 내용이 겹치는 확인 질문도 별도 메시지라면 각각 따로 넣는다." 추가. 서버 재시작 후 커넥터 재연결, 저장 요청 메시지 수정으로 새 분기 생성.
- 결과: 4차 호출(`24baf4be`) 20/20, assistantSummary 2,705자(새로 생성). 정답 대비 학습 발화 18개 일치, **5번째 발화 여전히 누락**. 늘어난 1개는 분기에 포함된 진단 메시지("이 대화에서 내가 보낸 다섯 번째 메시지를…")이며 정상 포함이다.
- 해석: 도구 설명 문구로는 교정되지 않았다. 해당 발화를 묻는 진단 메시지가 컨텍스트에 있었는데도 누락됐다.

#### answerGist(B안) 적용 후 요약 품질 평가 (세션 `ca3cbb00`, 원문 = Claude 공유 링크)

- 발화: 원문 5번째 확인 질문 **4번째 누락**(독립 시행 4회 모두). 분기에 포함된 저장 요청·진단 메시지 10건(19~28번)도 학습 발화로 섞여 들어왔다.
- 인용 답장 맥락 손실: 2번 "이건 먼지 간단 설명좀"은 원문에서 "클러스터 인덱스를" 인용 답장이었으나 커넥터 발화에는 인용 대상이 없다.
- 사용자가 헷갈린 지점 10곳 중 answerGist는 9곳의 교정을 담았다(누락 발화 1곳 제외). assistantSummary는 개념 정리 형식이라 "틀렸다"고 명시한 곳이 2곳(MVCC 스냅샷 주체, "작업 중이면 undo")뿐이다.
- assistantSummary 누락 핵심: 인덱스가 있어도 옵티마이저가 풀스캔을 고르면 전부 잠김 + EXPLAIN type ALL 확인(원문 2회 강조), 레코드 단위 점진 잠금으로 인한 부분 점유·데드락, 범위 끝 다음 레코드까지 잠김, RC에서도 유니크 중복 검사·FK 갭 락 존재, 세컨더리 인덱스 잠금 시 클러스터 인덱스도 잠김, gap only 락끼리 호환되어 INSERT 데드락, supremum·락 메모리·data_locks 확인법.
- assistantSummary 왜곡: next-key 표에 "READ COMMITTED → record lock만"으로 단순화했으나, 원문 AI는 "RC = 갭 락 없음으로 외우면 안 된다"고 경고했다.
- 결론: 오개념 신호의 1차 재료는 answerGist가 assistantSummary보다 낫다. assistantSummary만으로 복습 문제를 만들면 원문의 실무 핵심과 경고가 빠지고 일부는 반대로 학습된다.

- 채점기 보정: 금지 패턴에 "record only" 표기를 추가했다(v3 첫 채점의 금지 0건은 정규식 누락). 채점기는 v3 필드(`answerKeyPoints`)를 읽으므로 v2 이전 세션의 사실 점수는 위 표의 기록값을 쓴다.

#### 스키마 v5 짧은 대화 (커밋 `8d04746`, 세션 `dc514f8a`)

- 인자 3,569자 (v3 b2 4,139자 대비 -14%), 거부·재시도 없이 1회 성공. 발화 5/5, 의도 5/5, 핵심 사실 2/2.
- 생략 규칙 준수: meta 발화는 `{index, text, intent}`, 판정 없는 발화는 `aiVerdict` 생략. 반복 설명을 `turns [1, 4]`처럼 묶었다.
- 문제: corrected 발화 2·5번이 어느 `confusionPoints`에도 없었다(선택 필드가 되자 통째로 생략). `userBelief`가 사라졌다. → 검증 경고와 도구 설명 규칙 추가(다음 커밋).

#### v5 + confusionPoints 보완 (커밋 `106aa01`)

- 서버 재시작 후 첫 저장(`25ce3e67`)은 404(이전 MCP 세션) → 재연결 → 1초 뒤 같은 인자로 재전송됐다. 인자 재생성은 없었지만 `tools/list`를 다시 받지 않아 **이전 도구 설명으로 호출**됐고, confusionPoints가 비어 서버 경고 2건이 붙었다.
- 커넥터를 끊었다 다시 연결하자 `tools/list`를 새로 받았고(새 설명 확인), 새 대화 저장(`e612b590`)은 3,411자, 재시도 없음, 발화 5/5·의도 5/5·핵심 사실 2/2, **헷갈린 지점 2·5번 모두 포착**, 경고 0.
- 시사점: 도구 설명 변경은 이미 연결된 사용자에게 즉시 반영되지 않는다. 사용자가 커넥터를 다시 연결하거나 새 대화를 시작해야 한다. 서버 검증·경고를 최종 안전장치로 유지하고, MCP `tools/list_changed` 알림으로 Claude가 갱신하는지는 추후 확인한다.
